# Как устроено управление вентилятором

## Общая схема

```text
Пользователь
    │
    ▼
QTS GUI: Smart Fan / Fixed 50% / Fixed 100%
    │
    ▼
/etc/config/qfan.conf и /etc/config/uLinux.conf
    │
    ▼
hal_daemon — логика QNAP и температурные состояния
    │                         ▲
    │ читает профиль         │ события hal_event
    ▼                         │
/etc/model.conf ──────────────┘
    │
    │ [System FAN]
    │ FAN_UNIT=MCU
    │ FAN_1=I1:C0
    │ MIN_PWM=51
    │ MAX_PWM=178/255
    ▼
QNAP uLinux HAL / libuLinux_hal.so
    │
    ▼
I²C / MCU системной платы
    │
    ▼
4-pin PWM fan → tachometer → RPM в QTS
```

## Почему GUI 100 % не равнялся PWM 255

Интерфейс оперирует нормализованным диапазоном конкретной модели. Упрощённо:

```text
выход PWM = MIN_PWM + процент × (MAX_PWM - MIN_PWM)
```

Точная формула QTS может учитывать режим, ступени и температуры, но ключевой
факт такой: если `MAX_PWM=178`, никакая команда «100 %» не должна превысить
модельный потолок.

`qfan.conf` задаёт общую политику, а `model.conf` ограничивает её аппаратными
возможностями, заявленными для конкретного NAS.

## Зачем QNAP установил 178

Исследование не установило официальную причину. Возможные инженерные причины:

* шум штатного вентилятора;
* его паспортный диапазон;
* акустический профиль продукта;
* энергопотребление;
* конструкция корпуса;
* унификация профилей нескольких вариантов платы.

Это гипотезы, а не доказанные факты. Доказан только сам лимит и его влияние.

## Почему hwmon не помог

Обычные Linux-системы часто предоставляют:

```text
/sys/class/hwmon/hwmonN/pwm1
/sys/class/hwmon/hwmonN/fan1_input
```

На исследованном TS-230 `hwmon0` представлял `rtk_thermal`, а файлов fan/pwm
не было. QNAP получает RPM и управляет скоростью через собственный HAL/MCU,
поэтому отсутствие стандартного интерфейса закономерно.

## Почему найденный Realtek PWM не использовался

На SoC существовал контроллер `/sys/devices/platform/980070d0.pwm` с четырьмя
каналами. Но эксперимент дал два отрицательных признака:

1. Device Tree-узел `rtk_fan@9801BC00` имел `status=disabled`.
2. Ни один наблюдаемый канал не изменялся при переключении GUI 100 → 50 %.

Если управляющий параметр не коррелирует с известным воздействием, считать
его каналом вентилятора нельзя. Прямая запись могла бы затронуть другую
функцию платы.

## Что означало свойство Device Tree `pwms`

Байты:

```text
00 00 00 4c 00 00 00 01 00 00 93 f6
```

состоят из трёх 32-битных big-endian ячеек:

```text
controller phandle = 0x4c
PWM channel        = 1
period             = 37878 ns
frequency          ≈ 1 / 0.000037878 ≈ 26.4 kHz
```

Частота выглядит правдоподобно для 4-pin PWM fan, но `status=disabled` и
эксперимент важнее внешнего сходства.

## Что показал `libuLinux_hal.so`

Строки и символы:

```text
HM_Set_Fan_Speed_By_PWM
HM_Set_Fan_Speed
i2c_sys_set_root_fan_pwm
mcu_sys_set_fan_speed
se_sys_get_fan_pwm_min_max
/etc/model.conf
```

Они сформировали рабочую гипотезу: QTS читает модельные ограничения и передаёт
скорость MCU. Мы не вызывали функции библиотеки напрямую, потому что без
заголовков неизвестны ABI, аргументы и побочные эффекты.

## Почему enclosure API вернул `ret=-2`

`hal_app --se_enum` увидел root enclosure и один вентилятор, но вызовы
`--se_sys_get_fan` и `--se_sys_get_fan_pwm` вернули `ret=-2`, 0 RPM и 0 PWM.

Вероятные объяснения:

* этот API рассчитан на внешние enclosure;
* root backend TS-230 не реализует операцию;
* системный вентилятор обслуживается отдельным MCU API;
* требуются иные внутренние идентификаторы.

Результат был отрицательным, поэтому setter этого API не применяли.

## Роль `hal_event`

`hal_event` отправляет события работающему `hal_daemon`. Внутри бинарника была
обнаружена реальная последовательность QNAP:

```sh
/sbin/hal_event --se_set_fan_force_speed fan_level=7
/sbin/hal_event --se_clear_fan_force_speed
```

Она находилась рядом с обработкой снятия крышки корпуса. Это не означает, что
level 7 равен 100 %. Эксперимент показал:

```text
forced level 7/8/10: около 2800 RPM
после clear в QTS Fixed 100%: 2970 RPM
```

Значит force применяется временно, а `clear` возвращает исходную политику и
заодно заставляет HAL перечитать модельный предел.

## Почему пакет не держит forced mode

Постоянный force мог бы обойти Smart Fan и изменить поведение при охлаждении.
Пакет использует его только три секунды как триггер:

```text
установить временный level 7
             ↓
подождать 3 секунды
             ↓
очистить override
             ↓
QTS снова управляет вентилятором
```

## Жизненный цикл файла модели

```text
boot QTS
  ↓
создание /etc/model_Q04Z0_Q0500_10_10.conf
  ↓
создание /etc/model.conf symlink
  ↓
запуск enabled QPKG
  ↓
QNAP-PWM проверяет и меняет 178 → 255
  ↓
HAL force/clear
  ↓
обычная работа QTS
```

Из-за генерации `/etc` backup рядом с файлом может исчезнуть после reboot.
Именно поэтому persistence решается штатным startup package, а не надеждой на
сохранение изменённого `/etc/model.conf`.
