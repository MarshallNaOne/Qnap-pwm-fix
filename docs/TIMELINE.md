# Хронология расследования

Здесь шаги расположены в фактической логике исследования. Цель — показать не
только правильный ответ, но и почему выполнялась каждая проверка.

## Этап 1. Симптом

Новый ARCTIC P8 Slim PWM PST при GUI 100 % выдавал около 2200 RPM вместо
паспортных 3000. Возможные причины в начале:

* вентилятор или разъём не поддерживает полный диапазон;
* QFan ограничивает high PWM;
* QTS выдаёт не 100 %;
* драйвер SoC ограничивает duty cycle;
* MCU QNAP применяет модельный предел.

## Этап 2. Исключение QFan

Прочитали `/etc/config/qfan.conf`: `high_pwm=255`. Значит очевидный верхний
предел пользовательской политики уже был максимальным.

Одновременно `uLinux.conf` показывал Fixed 100. Это исключило ошибку выбора
режима в GUI.

## Этап 3. Поиск стандартного Linux-интерфейса

Проверили hwmon. Нашли только `rtk_thermal`, без `fan*`/`pwm*`. Вывод: QNAP
использует нестандартный backend.

## Этап 4. Device Tree и PWM-контроллер

Нашли Realtek fan/PWM-описания и расшифровали 26.4 kHz. Это выглядело
перспективно, но узел был disabled.

Прочитали четыре Realtek PWM-канала до и после GUI 100 → 50 %. Изменений не
было. Гипотеза прямого SoC PWM была отвергнута. В регистры не писали.

## Этап 5. Поиск QNAP HAL API

Изучили строки `hal_app`, `hal_util`, `hal_event`, `hal_daemon` и
`libuLinux_hal.so`.

Попытались прочитать root enclosure через `hal_app`. Получили `ret=-2`, поэтому
не стали пробовать setter на неподтверждённом backend.

На QTS отсутствовали `nm`, `readelf`, `objdump`; устанавливать binutils только
ради reverse engineering на рабочий NAS не стали. Вместо этого искали
потребителей функций через `strings`.

## Этап 6. Профиль модели

Связь `libuLinux_hal.so` с `/etc/model.conf` привела к секции `[System FAN]`.
В ней обнаружили `MAX_PWM=178`.

Математика и обороты согласовались, поэтому гипотеза получила конкретный и
безопасно проверяемый параметр.

## Этап 7. Первый успешный тест

Создали backup, изменили только `178 → 255`, затем переключили GUI 50 → 100.
Получили 2970 RPM. Причина была подтверждена.

## Этап 8. Как применить без GUI

Из `hal_event` нашли force/clear. Сначала `--show_internal` ничего не вывел.
Затем строки бинарника показали захардкоженный level 7.

Проверили уровни 7, 8 и 10: около 2800 RPM. После clear получили 2970 RPM.
Вывод: forced level не является желаемым постоянным 100 %, но force/clear
перечитывает текущую QTS-политику и новый предел.

Провели A/B-логику 178 ↔ 255 с force/clear. Механизм применения был найден.

## Этап 9. Persistence

После reboot ручная правка `/etc` исчезала. Рассматривались:

* `autorun.sh`;
* cron `@reboot`;
* ручная запись в `qpkg.conf`;
* настоящий QPKG.

Выбрали QPKG как штатный управляемый механизм QTS.

## Этап 10. Ручной service script

Создали `QNAP-PWM.sh` в `.qpkg`, добавили проверки и логирование. При ручном
запуске он успешно сделал 178 → 255 и HAL reload.

Затем вручную создали секцию `qpkg.conf` через `setcfg`. До reboot QTS subsystem
мог вызвать script через `qpkg_service start QNAP-PWM`.

## Этап 11. Неудача ручной регистрации

После reboot QTS добавил `Incomplete_Conf=1`, установил `Enable=FALSE`, а
`qpkgd` перестал считать пакет существующим. Вывод: набор строк в `qpkg.conf`
не заменяет штатную установку QPKG.

Эта ошибка была полезной: она доказала разницу между вызовом service script и
полноценной регистрацией приложения.

## Этап 12. Официальный QDK

Нашли официальную документацию QNAP и установили QDK 2.3.11.

Первая попытка `qbuild --create-env` внутри каталога установленного QDK дала
`Permission denied`. Создали рабочий каталог на data volume и продолжили без
sudo.

Первая архитектурная сборка `--build-arch arm_64 --strict` упала на пустом
`arm_64`. Поскольку payload — обычный shell, архитектурные каталоги удалили и
собрали generic QPKG.

`qbuild --query` показал пустые метаданные, что выглядело подозрительно.
Вместо предположений извлекли пакет: `qpkg.cfg`, standard `qinstall.sh` и
исполняемый payload были на месте. Вывод: query этой версии ненадёжен для
данного пакета, а структура корректна.

## Этап 13. CLI и code signing

`qpkg_cli -m` только распознавал internal name. Debug показал:

```text
cs_qpkg_verify_v2.sh ... -2:-2
```

Пакет останавливался до install queue. Были исследованы `-A/--ignore_cert`,
`QDevelop`, developer mode и строки `qpkgd`. Случайные значения `-A` не
помогли. Внутреннюю лицензию/проверку не обходили.

## Этап 14. Успешная установка

App Center → Install Manually показал штатное предупреждение об unsigned QPKG
и после явного подтверждения установил пакет.

Признаки успеха:

* `status_value=enabled`;
* `Enable=TRUE`;
* `Status=complete`;
* нет `Incomplete_Conf=1`;
* QTS создал `.list` и `.uninstall.sh`;
* service script автоматически стартовал при установке;
* журнал завершился `PWM patch successfully applied`.

## Этап 15. Репозиторий и воспроизводимая сборка

История, исходники и ручной helper были сохранены в Git.

Позже пакет пересобран официальным QDK 2.3.11 в Ubuntu 22.04. Попытка собирать
на macOS была отброшена: BSD `sed/tar` отличались от GNU-окружения и добавляли
macOS extended attributes. Linux-сборка была извлечена, а `qpkg.cfg` и payload
побайтово сравнены с исходниками.

| Подход | Результат | Решение |
| --- | --- | --- |
| GUI 100 % | ~2200 RPM | Симптом, не причина |
| `qfan.conf high_pwm=255` | Уже максимум | Искать ниже |
| hwmon | fan/pwm отсутствуют | Не применим |
| Realtek PWM sysfs | Не меняется с GUI | Не писать |
| `hal_app se_sys_get_fan*` | `ret=-2` | Backend не подходит |
| `model.conf MAX_PWM=178` | Объясняет ~70 % | Подтверждено |
| Ручное 178 → 255 + GUI | 2970 RPM | Успех |
| Force level 7 постоянно | ~2800 RPM, override | Не использовать постоянно |
| Force 7 → clear | Возврат к 2970 | Триггер HAL reload |
| Ручной `qpkg.conf` | Disabled после reboot | Не полноценный QPKG |
| QDK generic build | QPKG создан | Успех |
| `qpkg_cli -m` | Code-signing pre-check | Не рабочий путь здесь |
| App Center manual install | Enabled, service запущен | Успех |
